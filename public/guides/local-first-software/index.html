What local-first software means for your work

A task list is a record of what you are worried about, what your clients are called and what you have not done yet. Where that file lives is not a technical detail. It is the first question worth asking about the tool that holds it.

By Rajat Malik 17 November 2026

Where the term comes from

“Local-first software” was described in a 2019 essay by Martin Kleppmann, Adam Wiggins, Peter van Hardenberg and Mark McGranaghan, published by Ink & Switch under the title Local-first software: You own your data, in spite of the cloud. The essay set out seven ideals for software that keeps working on your device while treating the network as an enhancement rather than a requirement.

The phrase has since been used loosely, sometimes for anything that stores a cache. The useful version is narrower: the copy on your machine is the primary copy, not a convenience copy of somebody else's database.

The promises, plainly

In the essay's terms, the seven ideals are:

  1. No spinners. Your work is on screen immediately, because it is already there.
  2. Your work is not trapped on one device. It can move with you.
  3. The network is optional. The app is useful on a train with no signal.
  4. Seamless collaboration. Where there are other people, it works with them.
  5. The Long Now. The software keeps working, and the data keeps opening, for years.
  6. Security and privacy by default. Your data is not readable by a server you do not control.
  7. You retain ownership. You can take it out and use it elsewhere.

Not every app that calls itself local-first keeps all seven. Some keep the first, third and sixth and fail the seventh. Some sync beautifully and keep nothing else. The list is useful because it gives you something to check, rather than a badge to trust.

The trade a local-only app makes

There is a version of local-first that keeps all seven: local storage, optional sync, collaboration through a sync engine, and an export that opens anywhere. Building that is hard, and most tools that claim it have made a compromise somewhere.

There is a simpler version: the app keeps everything on your machine and does not sync at all. That keeps the first, third, sixth and seventh promises strongly, and gives up the second and fourth. It is not a lesser ambition; it is a different product. It suits data you would rather not put in somebody else's database more than it suits data you need on three devices at once.

The honest question

Not “is this local-first?” but “which of these promises does this tool keep, and which ones did it trade away?” A tool that says “no cloud” and a tool that says “syncs everywhere” are both making a choice. Neither is lying; you just need to know which choice you are getting.

How to check a tool

Six questions, in the order that will save you the most time:

  • Where is the file? A path you can open in a file manager is a better answer than “securely in the cloud”. If there is no file, ask what happens when the company stops.
  • What happens with the network off? Open the app with the Wi-Fi disabled and try to do real work. A local-first app is fully usable; a web app with a cache is usable until it is not.
  • Can you get everything out? Not a PDF and not a screenshot: a complete, machine-readable export. If the export is missing, the data is not really yours.
  • What leaves the device? Look for the telemetry, the crash reports, the analytics, the login. Some of these are reasonable; the point is to know.
  • Who can read it? A local database with no server is the strongest answer. End-to-end encryption is the next strongest. “We take security seriously” is not an answer.
  • Is it open source? Not a requirement, but a licence you can read is the difference between a promise and something you can check.

Backups are yours now

The advantage of local data is that nobody else holds it. The disadvantage is the same sentence: nobody else holds it. A cloud service's uptime and backups are part of what you pay for; with a local app, the copy is your responsibility.

That is not a reason to avoid local-first. It is a reason to take the export seriously and to know where the file is before you need to restore it. A backup you have never opened is a hope, not a backup. Once a month, export the data and open the file. It takes a minute and it is the difference between a scare and a loss.

One example, with its limits

DeepWork is a local-only application, and it is honest about which side of the trade it is on. The desktop build keeps everything in a local SQLite database; the web app keeps its data in the browser's own storage. There is no account, no DeepWork server and no sync. Every launch copies the database and its write-ahead log into a backups folder before migrations run, and a database that is present but unreadable stops startup rather than being replaced by an empty one.

That keeps the first, third, sixth and seventh promises well. It gives up the second and the fourth: there is no multi-device sync and no collaboration, by design. A full JSON backup restores everything on another machine, and tasks can be exported to CSV, so the data is portable even though it does not sync. The app is MIT-licensed, so the claim that you own it is one you can check.

If you need the same list on a laptop, a phone and a tablet at once, this is the wrong tool and the site says so. If you would rather the list of everything you are behind on lived on the machine in front of you, that is the case it was built for.
